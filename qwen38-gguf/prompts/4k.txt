# Lantern repository context

You are acting as a coding agent inside the fictional Lantern monorepo. Lantern is a small
multi-tenant job orchestration service used by a design-rendering company. A user submits a
render job, the API writes the job and an outbox record in PostgreSQL, a worker claims the job
from Redis, and the worker emits lifecycle events. The web dashboard consumes a compact event
stream over server-sent events (SSE). The repository is deliberately incomplete below: these
are the relevant excerpts from a checkout at commit `7b91e1a`.

The service is written in TypeScript with strict mode enabled. API requests may be retried by a
client, workers may crash and restart, and the same event may be delivered more than once. The
intended invariants are:

* a job has one logical state machine: queued -> running -> succeeded or failed, with cancelled
  allowed from queued or running;
* state transitions are monotonic in the event sequence, and a late event must never make a
  terminal job appear active again;
* every mutation carrying an idempotency key returns the same result on a retry;
* the outbox row and the corresponding state change commit atomically;
* the dashboard may reconnect with `Last-Event-ID` and must receive a coherent replay;
* a worker lease can expire, but only the current lease holder may publish a completion event;
* tenant data must never be read across tenant boundaries.

## Architecture notes

The API and workers run in separate processes but share the same PostgreSQL database. The
`job_events` table is the durable ordering source. Its `tenant_id, job_id, sequence` key is
unique, and `sequence` is allocated by the job row's `next_event_sequence` field while holding
the job row lock. The outbox publisher sends committed event payloads to Redis Streams. The API
SSE route reads the durable table for replay, then tails Redis for low latency. A browser can
disconnect between those two phases, so the route uses an event id encoded as `job_id:sequence`.

The current production issue is reported as: “after a flaky network retry, a completed render
occasionally returns to running in the dashboard, and a second retry sometimes creates a second
render.” The incident is most common when an API request times out after committing and a worker
finishes at nearly the same time. The task at the end asks you to diagnose this from the excerpts.

  tenantId: string;

  responseBody: unknown;
  createdAt: Date;

export function hashRequest(body: unknown): string {
  return createHash("sha256")
    .update(JSON.stringify(body, Object.keys(body as object).sort()))
    .digest("hex");
}

export function normalizeIdempotencyKey(raw: string | undefined): string | null {
  if (!raw) return null;
  const key = raw.trim();
  if (key.length === 0 || key.length > 200) return null;
  return key;
}

  type: z.literal("job.queued"),
  state: z.literal("queued"),
  payload: z.object({ inputUri: z.string(), renderer: z.string() }),

export const JobStarted = BaseEvent.extend({
  type: z.literal("job.started"),
  state: z.literal("running"),
  payload: z.object({ workerId: z.string(), leaseId: z.string() }),
});

export const JobProgress = BaseEvent.extend({
  type: z.literal("job.progress"),
  state: z.literal("running"),
  payload: z.object({ completed: z.number().int().nonnegative(), total: z.number().int().positive() }),
});

export const JobSucceeded = BaseEvent.extend({
  type: z.literal("job.succeeded"),
  state: z.literal("succeeded"),
  payload: z.object({ outputUri: z.string(), checksum: z.string() }),
});

export const JobFailed = BaseEvent.extend({
  type: z.literal("job.failed"),
  state: z.literal("failed"),
  payload: z.object({ errorCode: z.string(), message: z.string() }),

  type: z.literal("job.cancelled"),
  state: z.literal("cancelled"),
  payload: z.object({ reason: z.string() }),

  JobSucceeded,
  JobFailed,

}

  return event.state;

## `apps/api/src/domain/job.ts`

```ts
import { ConflictError, DomainError } from "../../../packages/shared/src/errors.js";
import type { JobEvent, JobState } from "../../../packages/events/src/job-events.js";

export interface Job {
  id: string;
  tenantId: string;
  state: JobState;
  inputUri: string;
  renderer: string;
  outputUri: string | null;
  failureCode: string | null;
  failureMessage: string | null;
  version: number;
  nextEventSequence: number;
  leaseId: string | null;
  leaseExpiresAt: Date | null;
  createdAt: Date;
  updatedAt: Date;
}

const terminal = new Set<JobState>(["succeeded", "failed", "cancelled"]);

export function isTerminal(state: JobState): boolean {
  return terminal.has(state);
}

export function assertTransition(current: JobState, next: JobState): void {
  if (current === next) return;
  if (isTerminal(current)) {
    throw new ConflictError(`cannot transition terminal job from ${current} to ${next}`, "terminal_job");
  }
  const valid: Record<JobState, JobState[]> = {
    queued: ["running", "cancelled"],
    running: ["succeeded", "failed", "cancelled"],
    succeeded: [],
    failed: [],
    cancelled: [],
  };
  if (!valid[current].includes(next)) {
    throw new DomainError(`invalid job transition ${current} -> ${next}`, "invalid_transition");
  }
}

export function applyEvent(job: Job, event: JobEvent): Job {
  if (event.jobId !== job.id || event.tenantId !== job.tenantId) {
    throw new DomainError("event does not belong to job", "event_scope");
  }
  if (event.sequence <= job.version) return job;
  assertTransition(job.state, event.state);
  return {
    ...job,
    state: event.state,
    version: event.sequence,
    outputUri: event.type === "job.succeeded" ? event.payload.outputUri : job.outputUri,
    failureCode: event.type === "job.failed" ? event.payload.errorCode : job.failureCode,
    failureMessage: event.type === "job.failed" ? event.payload.message : job.failureMessage,
    updatedAt: new Date(event.occurredAt),
  };
}
```

## `packages/queue/src/lease.ts`

```ts
import { randomUUID } from "node:crypto";
import { LeaseLostError } from "../../shared/src/errors.js";

export interface Lease {
  jobId: string;
  workerId: string;
  leaseId: string;
  expiresAtMs: number;
}

export interface LeaseStore {
  acquire(jobId: string, workerId: string, ttlMs: number): Promise<Lease | null>;
  renew(lease: Lease, ttlMs: number): Promise<boolean>;
  release(lease: Lease): Promise<void>;
  assertOwned(lease: Lease): Promise<void>;
}

export function newLease(jobId: string, workerId: string, ttlMs: number, now = Date.now()): Lease {
  return { jobId, workerId, leaseId: randomUUID(), expiresAtMs: now + ttlMs };
}

export async function withLease<T>(
  store: LeaseStore,
  lease: Lease,
  work: () => Promise<T>,
): Promise<T> {
  await store.assertOwned(lease);
  const result = await work();
  await store.assertOwned(lease);
  return result;
}

export function requireRenewed(ok: boolean): void {
  if (!ok) throw new LeaseLostError();
}
```

## API contract notes

The public `POST /v1/jobs` contract returns `202` and the complete job representation. The
client treats the response body as durable: it stores the returned job id and uses that id for
subsequent polling. It is therefore not acceptable for an idempotent retry to return a fresh
job with a different id, even if both requests have the same request body. A request hash must
include all fields that influence creation, but must not include headers such as tracing ids.

The event table is intended to be append-only. There is no trigger today preventing an event
with sequence 18 from being inserted before sequence 17, because workers and a future repair
tool can both write it. Consumers should tolerate a gap while replaying, but an SSE connection
should not silently claim that a gap is complete. The web UI currently assumes every live
notification is newer than its local state.

The worker's `claimNext` SQL is a legacy optimization from before the lease store was added.
The Redis lease implementation above is now used by a separate worker pool in another branch,
but this checkout still uses the `jobs.lease_id` column as its authoritative completion guard.
Do not blindly combine both lease designs in the minimal patch; decide which authority is
needed and explain how the other one should be retired or integrated.

## Request traces and edge cases

```text
request A: BEGIN
request A: SELECT idempotency_keys WHERE (tenant-a, render-42) -> no rows
request B: BEGIN
request B: SELECT idempotency_keys WHERE (tenant-a, render-42) -> no rows
request A: INSERT jobs(job-A), INSERT outbox(seq 1), INSERT idempotency(render-42)
request A: COMMIT; queue XADD(job-A); socket closes before HTTP response
request B: INSERT jobs(job-B), INSERT outbox(seq 1), INSERT idempotency(render-42)
request B: COMMIT; queue XADD(job-B); response 202 job-B
```

The trace above is produced by a test double whose `INSERT idempotency` does not model the
primary-key conflict. In PostgreSQL one insert would block and then fail with `23505`, so a
blind retry of the whole serializable transaction can accidentally create a second job unless
the retry path re-reads the idempotency row and compares the request hash. Also note that a
replayed key with a changed body must return a conflict, not the original response.

```text
worker W1: UPDATE jobs SET state=running, lease_id=L1, version=10 WHERE state=queued
worker W1: COMMIT; render continues for 40 seconds
worker W2: UPDATE jobs SET state=running, lease_id=L2, version=11 WHERE lease expired
worker W2: COMMIT; render succeeds; INSERT job.succeeded(seq 12); COMMIT
worker W1: UPDATE jobs SET state=succeeded, lease_id=NULL, version=12 WHERE lease_id=L1
           -> zero rows, but old code logs and continues in one error path
browser: receives seq 12 succeeded, then delayed seq 10 started
```

The correct result is one terminal projection and one terminal event. A stale worker may be
allowed to finish its expensive local render, but it must not mutate the job or publish a
success event after losing ownership. A failed conditional update is a normal domain result,
not a reason to emit an event using the stale `version` it read earlier.

The SSE route also has a boundary race: it queries rows through sequence 12, then subscribes
to Redis, while a publisher sends sequence 13 between those operations. A robust route either
subscribes before taking a replay watermark and filters duplicates, or performs a second durable
read after subscribing. The fix must retain tenant and job predicates on every read and should
not rely on a client-supplied `Last-Event-ID` job id to select authorization scope.
