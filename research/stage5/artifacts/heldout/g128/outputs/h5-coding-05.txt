The vulnerability described is a classic **Broken Access Control** or **Insecure Direct Object Reference (IDOR)** flaw. By only filtering on `id`, any authenticated user (Tenant A) can retrieve the job record belonging to Tenant B if they know or guess the `id`.

### 1. Corrected Predicate

The `WHERE` clause must include **both** the `id` and the `tenant_id` to ensure the caller can only access resources belonging to their own tenant.

**Corrected SQL Predicate:**
```sql
SELECT * FROM jobs 
WHERE id = $1 
  AND tenant_id = $2
```

> **Note:** In your application code, `$1` should be the `id` parameter, and `$2` should be the `tenant_id` derived from the **authenticated session context** (not from user input). Never trust the `tenant_id` passed by the client; always derive it from the server-side session/token.

---

### 2. Security Regression Assertion

**Scenario:**
- **Tenant A** (ID: `100`) has a job with `id = 42`.
- **Tenant B** (ID: `200`) also has a job with `id = 42`.
- An attacker (or bug) attempts to query the job with `id = 42` while authenticated as **Tenant B**.

**Assertion:**
> When querying for `id = 42` as **Tenant B** (`tenant_id = 200`), the query **must return zero rows** (empty result set), even though a job with `id = 42` exists in the database.
