To ensure robust idempotency in an API where JSON whitespace variations are common, the system must treat semantically identical payloads as identical. Here is the breakdown of the database rule, the hashing rule, and the behavioral logic.

### 1. Database Uniqueness Rule

The uniqueness constraint must be scoped to the **tenant** and the **logical endpoint** (route), using the **idempotency key** as the unique identifier for the request.

**SQL Constraint:**
```sql
CREATE UNIQUE INDEX idx_idempotency_unique 
ON idempotency (tenant_id, route, key);
```

**Rationale:**
- **`tenant_id`**: Ensures that two different tenants using the same `key` (e.g., "12345") do not collide.
- **`route`**: Ensures that the same `key` used for different endpoints (e.g., `POST /users` vs. `POST /orders`) is treated as distinct requests.
- **`key`**: The client-provided idempotency key (usually a UUID or a string provided by the client).

> **Note:** The `request_sha256` and `response` fields are **not** part of the uniqueness constraint. They are data fields stored *within* the row.
