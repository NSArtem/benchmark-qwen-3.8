The core issue here is that the "mark" (recording the intent) happens *before* the side effect (sending the message). If the process crashes after marking but before sending, the system believes the message was sent, but it actually wasn't. This violates the **at-least-once** guarantee because the message is effectively lost.

### The Problem with the Current Approach
1.  **Mark**: Record "Message M1 is sent" in the outbox table.
2.  **Crash**: Process dies.
3.  **Result**: Message M1 is never sent. The outbox shows it as "sent," so no retry mechanism will pick it up. **Message Loss.**

### The Smallest At-Least-Once Correction
To achieve **at-least-once** delivery, you must ensure that if a failure occurs, the message is **retried**. The current "mark before send" pattern prevents retry because the state is already "sent."

**The Correction:**
**Do NOT mark the message as "sent" in the outbox until the downstream service has successfully acknowledged the message.**

Instead, use a **two-phase commit** or **transactional outbox** pattern where:
1.  **Phase 1 (Local Transaction)**: Write the message to the `outbox` table with status `PENDING` (or `NEW`) in the **same database transaction** as the business data change.
2.  **Phase 2 (Asynchronous Dispatch)**: A separate, reliable dispatcher (e.g., a background job, a message queue, or a polling service) reads `PENDING` messages from the outbox and sends them to the downstream service.
3.  **Phase 3 (Acknowledgment)**: Only **after** the downstream service returns a success acknowledgment, update the outbox
