### Minimal Ordering Fix

**Fix:** The server must **subscribe to the live event stream before taking the durable snapshot**.

**Sequence:**
1.  **Subscribe** to the live event stream (start listening for new events).
2.  **Take** the durable snapshot at cursor 40.
3.  **Replay** events from the snapshot (events 1–40).
4.  **Deliver** live events (events 41+).

---

### Explanation of the Overlap Check

The overlap check guarantees **exactly-once delivery** (no duplicates, no gaps) by ensuring that the boundary between the historical snapshot and the live stream is **atomic and non-overlapping**.

#### Why the Original Order Fails
In the original order (Snapshot → Subscribe):
1.  Snapshot is taken at cursor 40.
2.  Event 41 is published.
3.  Subscription starts.

**Problem:**
- The snapshot contains events 1–40.
- The live stream starts listening *after* the snapshot is taken.
- If Event 41 is published **between** the snapshot and the subscription, it is **not** in the snapshot (because the snapshot was taken before it existed) and **not** in the live stream (because the subscription started after it was published).
- **Result:** Event 41 is **lost**.

#### How the Fixed Order Guarantees No Duplicates
In the fixed order (Subscribe → Snapshot):
1.  Subscription starts.
2.  Snapshot is taken at cursor 40.
3.  Event 41 is published.
