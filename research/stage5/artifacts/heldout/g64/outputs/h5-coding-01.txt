To ensure reliable idempotency in the presence of non-semantic JSON variations (like whitespace, key ordering, or number formatting), the system must decouple the *logical* content of the request from its *syntactic* representation.

Here are the specific rules for the database, hashing, and behavior:

### 1. Database Uniqueness Rule
The uniqueness constraint must be scoped to the **logical identity** of the request, not the raw byte string.

*   **Unique Index:** `(tenant_id, route, key)`
*   **Rationale:**
    *   `tenant_id`: Isolates data per customer/organization.
    *   `route`: Identifies the specific API endpoint (e.g., `POST /orders`).
    *   `key`: The client-provided idempotency key (a UUID or string).
*   **Implication:** If a client sends the *same* idempotency key to the *same* route for the *same* tenant, the database will reject the second insert if the logical request has changed. This enforces that an idempotency key can only be used for one specific logical operation.

### 2. Canonicalization Rule for Hashing
The `request_sha256` column must store the SHA-256 hash of the **canonicalized JSON body**, not the raw request body.

*   **Canonicalization Process:**
    1.  **Parse** the incoming JSON body into a data structure (e.g., a dictionary/object).
    2.  **Normalize** the structure:
        *   **Sort Keys:** Recursively sort all object keys in lexicographic order.
        *   **Normalize Numbers:** Convert all numbers to a consistent representation (e.g., always use integers if possible, or a fixed decimal
