### 1. The Ordering Invariant

The **ordering invariant** for a job state machine in a browser reducer is that **state transitions must be monotonically increasing with respect to sequence numbers.**

*   **Rule:** A state transition is only valid if the incoming event’s sequence number is **strictly greater** than the current state’s sequence number.
*   **Rationale:** This ensures that the client’s view of the job’s lifecycle is consistent with the server’s chronological order. If an event with a lower sequence number arrives after a higher one has already been processed, it is considered "stale" or "out-of-order" and must be ignored to prevent the UI from regressing (e.g., showing "Started" after "Succeeded").

### 2. The Terminal-State Guard

The **terminal-state guard** is a rule that **prevents any state transition once the job has reached a terminal state.**

*   **Rule:** If the current state is a terminal state (e.g., `succeeded`, `failed`, `canceled`), **no further events are allowed to modify the state**, regardless of their sequence number or type.
*   **Rationale:** Terminal states represent the final outcome of a job. Allowing subsequent events to change the state from `succeeded` back to `running` or `started` would violate the semantic integrity of the job’s lifecycle. The state is "frozen."
