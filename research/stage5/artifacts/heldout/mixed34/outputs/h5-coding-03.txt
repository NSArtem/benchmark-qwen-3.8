The scenario described is a classic failure case in distributed systems involving the **Transactional Outbox Pattern**.

### The Problem
1.  **Step 1:** The application writes a business transaction (e.g., `Order`) and an `OutboxMessage` into the same database transaction.
2.  **Step 2:** The outbox publisher picks up the message and marks it as `SENT` (or updates a status flag) in the database.
3.  **Crash:** The process crashes **after** Step 2 but **before** the downstream service (e.g., Kafka, RabbitMQ, or an HTTP API) actually receives the message.

**Result:** The message is marked as `SENT` in the outbox table, but it was never delivered. The publisher will skip it on the next run because it is already marked `SENT`. This violates **at-least-once** semantics because the message is lost.

---

### The Smallest At-Least-Once Correction

The smallest correction is to **decouple the "mark as sent" action from the "delivery" action** and ensure that the mark only occurs **after** successful delivery.

However, since the crash happens *after* the mark but *before* the call, the fix must ensure that **if the delivery fails or the process crashes, the message is not permanently marked as sent.**

#### ✅ Proposed Fix: **Idempotent Delivery with Post-Delivery Commit**

Instead of marking the message as `SENT` *before* sending it, you must:

1.  **Do NOT mark the message as `SENT` in the database before delivery.**
2.  **Deliver the message** to the downstream service (e.g., publish to Kafka, send HTTP request).
3.  **Only after successful delivery**, mark the message as `SENT`
