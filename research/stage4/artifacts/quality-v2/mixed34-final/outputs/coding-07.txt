**Test: `test_concurrent_idempotent_retry_with_delayed_worker`**

**Setup:**
1.  **Database:** In-memory SQLite.
2.  **Schema:** `orders(id, status, payload)`, `outbox(id, order_id, event_type, payload)`.
3.  **Worker:** A background task that processes `outbox` events. Inject a 500ms artificial delay before the worker commits the `orders` table update.
4.  **Client:** Two concurrent HTTP clients.

**Execution:**
1.  Send `POST /orders` with `Idempotency-Key: key-123` (Request A).
2.  Simultaneously send `POST /orders` with `Idempotency-Key: key-123` (Request B).
3.  Both requests hit the API. The API creates the order row and inserts an `outbox` event.
4.  The worker picks up the event. Due to the 500ms delay, Request B arrives *before* the worker commits the status change for Request A.
5.  Request B checks the idempotency key. It finds the existing order (created by A) but sees the status is still `pending` (not `committed`) because the worker hasn't finished.
6.  **Critical Logic:** The system must recognize the key exists and return the *original* response (200 OK) for Request B, rather than creating a duplicate or failing.
7.  Worker completes commit.

**Assertions:**
1.  **Idempotency Integrity:** `assert db.count("SELECT * FROM orders WHERE idempotency_key = 'key-123'") == 1`
    *   *Rationale:* Proves no duplicate order row was created despite concurrent writes.
2.  **Outbox Uniqueness:** `assert db.count("SELECT * FROM outbox WHERE order_id = (SELECT id FROM orders WHERE idempotency_key = 'key-123')") == 1`
    *   *Rationale:* Proves exactly one event was published. The second request did not trigger a second outbox entry.
