**Uniqueness Requirements**
The database must enforce a **unique constraint** on the `idempotency_key` column. This ensures that only one record can exist for a specific key. If a second request with the same key arrives, the database rejects the duplicate insertion, preventing double-processing (e.g., double-charging a customer).

**Atomicity Requirements**
The operation must be **atomic**, meaning the entire transaction succeeds or fails as a single unit. Specifically, the system must atomically check for the existence of the key and insert the new record. If the check passes but the insert fails (or vice versa), the transaction must roll back completely to maintain data integrity.

**Race Condition Resolution**
When two requests race, the database’s unique constraint acts as the final arbiter.
1. **Request A** checks the key (not found) and begins insertion.
2. **Request B** checks the key (not found, because A hasn’t committed yet) and begins insertion.
3. **Request A** commits successfully.
4. **Request B** attempts to commit but fails due to the **unique constraint violation**.

To handle this gracefully, the application must catch the unique constraint error (e.g., `SQLIntegrityConstraintViolationException` or `UniqueViolationError`) and treat it as a success by returning the response from the already-committed Request A. This ensures that the second request does not cause an error to the client, preserving the idempotent contract.

**Summary**
- **Uniqueness**: Enforced via a database unique index/constraint on the idempotency key.
- **Atomicity**: Ensured by wrapping the check-and-insert logic in a single transaction.
- **Conflict Handling**: Catch unique constraint violations during the atomic commit and return the existing response to the client.
