**Completion Predicate**
The worker must verify that the current `lease_token` stored in the database matches the token held in its local context. If they differ, the worker is no longer the active owner.

**Fencing Mechanism**
Use a conditional atomic update (optimistic locking) in the database. The `publish_success` operation must include a `WHERE` clause checking the token:

```sql
UPDATE jobs 
SET status = 'SUCCESS', finished_at = NOW() 
WHERE id = :job_id AND lease_token = :local_token;
```

**Fencing Logic**
1. **Worker A** attempts to publish with its original token `T_A`.
2. **Worker B** has already acquired the job, updating the database `lease_token` to `T_B`.
3. The database executes the `UPDATE` statement.
4. Since `T_A` does not match the current stored `T_B`, the `WHERE` clause fails.
5. The database returns `rows_affected = 0`.
6. **Worker A** detects the zero-row update and aborts the publish, preventing a double-write or stale success.

**Redis Alternative**
If using Redis, store the token in a key (e.g., `job:{id}:token`). Use a Lua script to atomically compare and update. If the stored token differs from the provided token, the script returns `0` (failure), fencing the stale worker.

**Conclusion**
The predicate is `db_token == local_token`. The mechanism is a conditional atomic write that fails if the token has changed, ensuring only the current lease holder can commit state changes.
