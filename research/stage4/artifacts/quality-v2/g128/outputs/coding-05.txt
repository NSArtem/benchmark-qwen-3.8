The race condition arises because the initial batch of durable events (PostgreSQL) and the live stream (Redis) are fetched separately. If a client disconnects after reading the durable batch but before subscribing to Redis, it misses events published in that gap.

**The Fix:**

1.  **Monotonic Sequence:** Assign a strictly increasing, global sequence number (e.g., `seq_id`) to every event. This number must be consistent across both storage systems. When an event is persisted to PostgreSQL, it receives a `seq_id`. When that event is subsequently published to Redis Streams, it carries the same `seq_id` in its payload.

2.  **Last-Event-ID:** The client sends `Last-Event-ID` (the `seq_id` of the last event it successfully processed) in the `Last-Event-ID` header upon reconnection.

3.  **Overlap & De-duplication:**
    *   **Reconnect Logic:** The server uses `Last-Event-ID` to determine the starting point.
    *   **Durable Catch-up:** Query PostgreSQL for events where `seq_id > Last-Event-ID`.
    *   **Live Subscription:** Subscribe to Redis Streams, but filter out any incoming events where `seq_id <= Last-Event-ID`.
    *   **De-duplication:** Since the same logical event exists in both systems (durable and stream), the client may receive duplicates if the overlap window is not handled. The client maintains a local cache of recently processed `seq_id`s. If an event arrives with a `seq_id` already in the cache, discard it.

This ensures no event is lost (gap covered by durable catch-up) and no event is processed twice (overlap handled by de-duplication).
