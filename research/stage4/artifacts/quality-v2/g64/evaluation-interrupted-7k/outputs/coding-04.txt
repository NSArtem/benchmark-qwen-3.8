To fence Worker A, the system must verify that the specific **lease token** held by the worker matches the **current active lease token** stored in the database for that job.

### 1. Minimal Completion Predicate

The predicate for a worker to successfully publish a result is:

```text
PUBLISH_SUCCESS(job_id, worker_token) = 
    (Current_Lease_Token_in_DB[job_id] == worker_token)
```

If this predicate evaluates to `true`, the worker is the current lease holder and may commit the result. If `false`, the worker has been superseded (fenced) and must discard the result.

### 2. Database/Redis Mechanism

The fencing mechanism relies on **atomic compare-and-swap (CAS)** or **conditional update** operations.

#### Option A: SQL Database (PostgreSQL/MySQL)

Use a conditional `UPDATE` statement that only succeeds if the stored token matches the worker's token.

```sql
-- Worker A attempts to publish success with token 'token_A'
UPDATE jobs
SET status = 'COMPLETED',
    result = <payload>,
    completed_at = NOW()
WHERE id = <job_id>
  AND lease_token = 'token_A';  -- Fencing check
```

- **If `lease_token` in DB is `'token_A'`**: The update succeeds (1 row affected). Worker A commits.
- **If `lease_token` in DB is `'token_B'`** (because Worker B acquired the lease): The `WHERE` clause fails. 0 rows affected. Worker A is fenced and must abort.
