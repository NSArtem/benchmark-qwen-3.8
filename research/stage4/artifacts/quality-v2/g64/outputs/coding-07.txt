**Test: Timeout-After-Commit Retry Integrity**

**Setup:**
1.  Initialize a clean database with an empty `orders` and `outbox` table.
2.  Configure the application’s transactional outbox pattern.
3.  Inject a delay into the worker’s commit hook (e.g., 500ms) to simulate a client-side timeout before the transaction fully persists.
4.  Send two concurrent `POST /orders` requests using the same `Idempotency-Key: test-123`.
5.  Wait for both requests to complete (one succeeds, one times out).
6.  Trigger the outbox worker to process pending events.

**Assertions:**
1.  **Database State:** Query the `orders` table. Assert that exactly **one** row exists for `Idempotency-Key: test-123`. The status of this single row must be `COMMITTED`.
2.  **Outbox Integrity:** Query the `outbox` table. Assert that exactly **one** event record exists for the same idempotency key. This ensures no duplicate side-effects were generated by the timed-out request.
3.  **Worker Behavior:** Assert that the worker processed the single outbox event successfully, updating the order status to `PROCESSED` in the main table.

**Conclusion:**
This test validates that the system correctly handles client-side timeouts after a successful commit. By enforcing idempotency at the database level and ensuring the outbox contains only unique, valid events, we guarantee that retries do not result in duplicate data or double-processing of side effects. The 500ms delay simulates real-world network latency or client impatience, proving the architecture’s resilience.
