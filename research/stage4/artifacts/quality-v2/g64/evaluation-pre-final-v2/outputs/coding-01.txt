**Diagnosis:**
The current implementation suffers from a classic check-then-act race condition. Two concurrent requests execute the `SELECT` simultaneously before either performs the `INSERT`. Both find no existing row, proceed to insert, and violate the unique constraint on the idempotency key. This results in one request succeeding and the other failing with a duplicate key error, rather than returning the original result.

**Smallest Database-Level Fix:**
Replace the check-then-act pattern with an atomic upsert using `INSERT ... ON CONFLICT DO NOTHING` (PostgreSQL) or `INSERT IGNORE` (MySQL). This ensures the database handles the concurrency atomically. If the key already exists, the insert is silently ignored, and no error is raised.

**Retry Mechanism:**
1.  **Attempt Insert:** Execute the atomic upsert.
2.  **Check Status:** Inspect the command's affected row count or specific return status.
3.  **If Inserted:** Process the job and return the newly generated result.
4.  **If Ignored (Conflict):** The key already exists. Execute a `SELECT` to retrieve the stored result from the existing row.
5.  **Return:** Return the original result from the first successful request.

This approach eliminates the race condition by delegating concurrency control to the database engine, ensuring that concurrent requests with the same idempotency key consistently return the same result without application-level locking or complex transaction management.
