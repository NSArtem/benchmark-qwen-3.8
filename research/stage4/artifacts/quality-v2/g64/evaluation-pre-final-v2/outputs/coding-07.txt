**Test: Timeout-After-Commit Retry Integrity**

**Setup:**
1.  **Environment:** PostgreSQL with `READ_COMMITTED` isolation.
2.  **API:** `POST /orders` accepting `Idempotency-Key: "key-123"`.
3.  **Worker:** A background processor that simulates a 5-second delay before committing the transaction.
4.  **Client:** Two concurrent HTTP clients sending the same payload with `Idempotency-Key: "key-123"`.
5.  **Trigger:** Client A times out after 2 seconds (before the worker commits) and immediately retries. Client B waits for the initial response.

**Execution:**
1.  Launch Client A and Client B simultaneously.
2.  Client A receives a `504 Gateway Timeout` after 2 seconds.
3.  Client A retries the request.
4.  Wait for the worker to complete the commit (5 seconds).
5.  Inspect the database state.

**Assertions:**
1.  **Single Commit:** The `orders` table contains exactly **one** row with `idempotency_key = 'key-123'`. No duplicate rows exist.
2.  **Consistent State:** The single row’s `status` field is `"COMPLETED"`, and the `created_at` timestamp matches the *first* request’s initiation time, not the retry time.

**Rationale:**
This test verifies that the system correctly handles client-side retries following a timeout that occurs *after* the server has already committed the transaction. It ensures the idempotency key prevents duplicate processing and that the response to the retry reflects the original, already-committed state, guaranteeing data integrity under concurrent, delayed-commit scenarios.
