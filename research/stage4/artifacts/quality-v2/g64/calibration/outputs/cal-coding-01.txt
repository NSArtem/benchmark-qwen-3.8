To handle racing requests with the same idempotency key, the database must enforce two core requirements:

1.  **Uniqueness**: The idempotency key must be a unique constraint (e.g., a unique index or primary key) on the relevant table. This ensures that only one record can exist for a specific key. If a second request attempts to insert a duplicate key, the database rejects it, preventing double-processing.

2.  **Atomicity**: The operation must be atomic. This means the entire transaction (inserting the result and updating any related state) must succeed or fail as a single, indivisible unit. If the first request fails after acquiring the key, the transaction must roll back completely, releasing the key so a subsequent retry can succeed. This prevents "zombie" states where the key is locked but no valid result exists.

Together, these requirements ensure that:
-   **Uniqueness** prevents duplicate side effects (e.g., double charging).
-   **Atomicity** ensures consistency; if the first attempt fails, the system remains in a clean state, allowing the idempotent key to be reused safely.

Without atomicity, a failed first request could leave the key "reserved" without a result, blocking valid retries. Without uniqueness, both racing requests could succeed, leading to duplicate actions. Implementing both guarantees that exactly one request succeeds, and all others receive the cached result of the first, maintaining data integrity under concurrency.
